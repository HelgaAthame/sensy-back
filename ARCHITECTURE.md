# Архитектура и реализация Sensy Backend

Этот документ объясняет **что уже построено и почему именно так** — в дополнение к [BACKEND_PLAN.md](./BACKEND_PLAN.md), который описывает контракт API и план по фазам. Если план — это "что и когда делать", то этот файл — "как оно на самом деле устроено внутри".

## 1. Что за продукт

Sensy — система контроля качества звонков колл-центра. Оператор загружает запись разговора, бэкенд:

1. распознаёт речь по каналам (кто оператор, кто клиент);
2. определяет, где были негативные эмоции, паузы, перебивания;
3. ищет в тексте фразы из настраиваемых словарей (стоп-слова, обязательные фразы и т.п.);
4. просит GPT (Groq) кратко резюмировать звонок и оценить его по чек-листам качества;
5. отдаёт всё это фронту — карточка звонка, список с фильтрами/сортировкой, аналитический дашборд.

Оригинальный бэкенд был утерян безвозвратно — этот написан с нуля, а контракт API реконструирован из RTK Query слоя фронтенда (см. раздел 3 [BACKEND_PLAN.md](./BACKEND_PLAN.md)).

## 2. Стек и почему именно он

| Слой | Выбор | Почему |
|---|---|---|
| Фреймворк | **NestJS + TypeScript** | модули/DI из коробки, декларативная валидация через DTO, легко растить по фичам |
| ORM | **Prisma** | типобезопасность, читаемые миграции, схема — единый источник истины |
| БД (прод) | **Neon** (serverless PostgreSQL) | бесплатный тариф без карты |
| БД (локально) | **Postgres в Docker** | идентичное поведение с продом |
| Очередь фоновых задач | **BullMQ + Redis** | загрузка звонка не должна ждать распознавание речи — тяжёлая обработка уходит в фон |
| Redis (прод) | **Upstash** | бесплатный managed Redis, TLS, без карты |
| Хранилище файлов | **MinIO** (локально) / **Backblaze B2** (прод) | оба S3-совместимые — один и тот же клиент `@aws-sdk/client-s3` работает с обоими без переключения кода |
| STT (распознавание речи) | **Whisper (`Xenova/whisper-tiny`) через `@xenova/transformers`** | ONNX-инференс прямо в Node.js, без Python-рантайма и без платного API |
| Тональность/эмоции | **`onnx-community/wav2vec2-base-Speech_Emotion_Recognition-ONNX`**, тот же движок transformers.js | тоже self-hosted и бесплатно; ограничение — модель англоязычная, см. раздел 8 |
| GPT-функции (саммари, авто-чек-лист) | **Groq API** (`llama-3.3-70b-versatile`) | единственный не-self-hosted компонент — осознанное отступление, см. раздел 8 |
| Документация API | **`@nestjs/swagger`** | автогенерация OpenAPI прямо из декораторов контроллеров/DTO, всегда актуальна |
| Контейнеризация | **Docker (multi-stage) + docker-compose** | одинаковое окружение локально и на Render |

## 3. Карта модулей (`src/`)

```
src/
├── auth/            JWT-логин (signin), guard для остальных модулей
├── operators/        CRUD операторов
├── projects/          CRUD проектов (объединяют словари + чек-листы)
├── dictionaries/      CRUD словарей фраз (Vocabulary)
├── checklists/        CRUD шаблонов чек-листов
├── media-files/       загрузка звонков, список, карточка, стрим аудио, результаты анализа
├── analysis/          ML-пайплайн: STT, тональность, поиск по словарям, паузы/перебивания
├── gpt/               GPT-саммари и авто-оценка чек-листов через Groq
├── dashboard/         агрегаты для аналитической страницы
├── storage/           абстракция над S3-совместимым хранилищем (MinIO/Backblaze B2)
├── prisma/            PrismaService (глобальный модуль)
└── common/            общий exception filter
```

Модули общаются через явные NestJS-импорты (`MediaFilesModule` импортирует `AnalysisModule` и `GptModule`), общее состояние — только через БД и Redis-очереди, не через прямые вызовы сервисов между доменами.

## 4. Модель данных (Prisma)

Ключевые таблицы и их назначение:

| Таблица | Назначение |
|---|---|
| `User` | учётка для входа (email/password → JWT) |
| `Operator`, `Project` | справочники |
| `Dictionary` + `DictionaryProject` | словари фраз, привязанные к проектам (many-to-many) |
| `Checklist` + `ChecklistProject` | шаблоны чек-листов, привязанные к проектам |
| `MediaFile` | звонок: метаданные (длительность, каналы), денормализованные агрегаты для сортировки списка (`negativeLevelOverall`, `keywordsCount`, `maxSimultaneousSilenceDuration`, `simultaneousSpeechCount`) |
| `MediaFileResult` | тяжёлые результаты анализа одним звонком: `stt`, `tonal`, `simultaneousSpeech`, `simultaneousSilence`, `keywordsSearchResult`, `summaryAnalyserResult` (jsonb), `gptSummary` |
| `MediaFileChecklist` | оценка конкретного чек-листа для конкретного звонка (изначально от GPT, правится оператором) — по одной записи на пару (звонок, чек-лист) |

**Почему jsonb, а не нормализованные таблицы для результатов анализа**: структура (`stt.chunks[]`, `tonal.regions[]` и т.д.) вложенная, читается целиком на карточку звонка, не требует реляционных запросов по отдельным сегментам. А то, по чему реально нужна быстрая сортировка списка звонков (`GET api/v2/mediafile?orderByDescNegativeLevel=true` и т.п.) — вынесено в обычные колонки `MediaFile`, чтобы Postgres мог использовать индекс/сортировку напрямую, не разбирая jsonb на каждый запрос.

**`summaryAnalyserResult`** считается один раз в конце ML-пайплайна и кладётся готовым jsonb-блоком в `MediaFileResult` — чтобы список звонков и дашборд не пересчитывали агрегаты (средние длительности пауз, разбивку по оператору/клиенту и т.д.) на каждый GET-запрос.

## 5. Асинхронный пайплайн анализа звонка

Это ядро системы — `src/analysis/analysis.processor.ts`, воркер BullMQ на очереди `media-analysis`.

### 5.1 Что происходит при загрузке звонка

1. `POST api/mediafile` (`media-files.service.ts`) — сохраняет файл в S3-хранилище, создаёт строку `MediaFile` со статусом `Processing`, ставит задачу в очередь `media-analysis` **с жёстким таймаутом 5 секунд** поверх `queue.add()` — если Redis недоступен или тормозит, загрузка звонка всё равно не подвиснет, просто анализ не запустится (см. раздел 7 про инцидент с Redis).
2. HTTP-ответ уходит сразу же, дальше — фоновая обработка.

### 5.2 Сам анализ (по шагам, `AnalysisProcessor.process`)

Для каждого канала (0 — оператор, 1 — клиент; конвенция телефонии) **последовательно** (не параллельно — см. раздел 7 про OOM на Render):

1. **Разделение канала** (`AudioService.splitChannel`) — ffmpeg pan-фильтр вырезает один канал из стерео-файла, ресемплирует в 16кГц (частота, которую ожидает Whisper).
2. **Декодирование в Float32Array** (`AudioService.readWavAsFloat32`) — через пакет `wavefile`, потому что `@xenova/transformers` в Node.js (в отличие от браузера) не может сам прочитать аудиофайл — ему нужен уже готовый массив сэмплов.
3. **STT** (`SttService.transcribeChannel`) — Whisper с `return_timestamps: true`, получаем текст и чанки с тайм-кодами (`{startTime, endTime, text}`).
4. **Поиск по словарям** (`KeywordSearchService.search`) — обычный поиск подстроки (без ML) по расшифровке, с фильтрацией словарей по типу (`OnlyOperator`/`OnlyClient`/`All`/`Hotwords`) и маппингом найденной фразы обратно на тайм-код через чанк, в который попало совпадение.
5. **Тональность** (`TonalService.classifyChunks`) — для каждого STT-чанка вырезается соответствующий кусок аудио и классифицируется ONNX-моделью эмоций (6 классов: SAD/ANGRY/DISGUST/FEAR/HAPPY/NEUTRAL). `prob` = суммарная вероятность "негативных" классов, `type = 1`, если `prob >= 0.5`.

После обработки обоих каналов:

6. **Паузы и перебивания** — вместо отдельной VAD-модели интервалы речи берутся прямо из тайм-кодов Whisper-чанков (`mergeIntervals`). `simultaneousSpeech` = пересечение речевых интервалов двух каналов (`intersectIntervals`) — оба говорят одновременно. `simultaneousSilence` = дополнение объединения обоих каналов до полной длительности звонка (`complementIntervals`) — никто не говорит.
7. **`summaryAnalyserResult`** — считаются все агрегаты одним проходом: суммы/средние длительностей речи и пауз, разбивка по каналу оператор/клиент, `negativeLevelOverall/Operator/Client` (взвешенное по длительности среднее `prob` из тональности), счётчик найденных фраз по названию словаря.
8. Всё пишется в `MediaFileResult` (upsert), денормализованные поля — в `MediaFile`, статус меняется на `Ready`.
9. Если что-то на любом шаге упало — `catch` ставит `status = 'Failed'`, `isFailed = true`, `failureReason` = текст ошибки. Остальной API это не роняет.

### 5.3 Почему такие модели

- **`Xenova/whisper-tiny`** — самая маленькая версия Whisper. При ожидаемой нагрузке (~10 звонков/день) точность важнее, но `tiny` — компромисс ради вписывания в CPU-only free tier по памяти и скорости; апгрейд до `whisper-base`/`whisper-small` — тривиальная замена строки модели, если понадобится точность.
- **SER-модель англоязычная** — готовой ONNX-модели распознавания эмоций для русской речи, совместимой с `transformers.js`, на момент реализации не существует. Акустические признаки (тон, темп, громкость) переносятся между языками лучше, чем текстовые, но точность на русской речи не гарантирована — это осознанный компромисс, а не недосмотр.

## 6. GPT-функции (`src/gpt/`)

Отдельная очередь BullMQ (`gpt-analysis`), запускается по требованию через `POST api/mediafile/:id/gpt-analysis` (**202 Accepted**, не блокирует запрос) — то есть GPT не считается автоматически при каждой загрузке звонка, только когда оператор открыл карточку и явно попросил.

`GptAnalysisService.runAnalysis`:

1. Собирает расшифровку из `MediaFileResult.stt.chunks`, размечая реплики как `[Оператор]`/`[Клиент]`.
2. Одним запросом к Groq (`GroqClient.completeText`) получает краткое саммари звонка на русском (3-5 предложений) → `MediaFileResult.gptSummary`.
3. Для каждого **активного** чек-листа, привязанного к проекту звонка — отдельным запросом (`GroqClient.completeJson`, JSON-режим Groq) просит модель оценить каждый критерий (`score` в диапазоне `[minScore, maxScore]` + `comment`, объясняющий оценку). Сервер сам считает суммы `score`/`minScore`/`maxScore` на уровне блока и чек-листа — модели не доверяется арифметика, только оценка конкретных критериев.
4. Результат по каждому чек-листу — отдельная запись в `MediaFileChecklist` (ключ — пара `mediaFileId + checklistId`).

`PUT api/mediafile/:id?checklistId=X` — оператор правит/подтверждает оценки поверх GPT: тело запроса с обновлёнными `score`/`comment` пересобирается в ту же структуру и полностью замещает предыдущую запись `MediaFileChecklist` (агрегаты пересчитываются на сервере заново, а не доверяются фронту).

`GET api/mediafile/:id/result` собирает `gptChecklist.collection` из всех `MediaFileChecklist` этого звонка — GPT-оценка и правка оператора живут в одной и той же записи, правка полностью замещает предыдущее состояние.

## 7. Инфраструктурные уроки (почему код выглядит именно так)

Несколько вещей в коде существуют из-за реальных инцидентов при разработке — стоит знать, зачем они там:

- **`node:22-slim`, а не `node:22-alpine`** (`Dockerfile`) — `onnxruntime-node` (нужен `@xenova/transformers`) поставляется прекомпилированным под glibc и не грузится на musl (Alpine).
- **`sharp` заменён на no-op заглушку** через npm `overrides` (`stubs/sharp/`) — это неиспользуемая транзитивная зависимость `@xenova/transformers` (нужна только для vision-моделей), но её нативный `libvips`-бинарник стабильно не докачивался на сборочном канале.
- **Постановка задачи в очередь обёрнута в `Promise.race` с таймаутом 5с** (`media-files.service.ts`) и **`enableOfflineQueue: false` + редкий бэкофф на реконнект** (`app.module.ts`) — при недоступном Redis `ioredis` по умолчанию переподключается бесконечно, и без этих защит `POST api/mediafile` зависал на неопределённое время вместо быстрого ответа.
- **`REDIS_URL` парсится с учётом `username`/`password`/TLS-схемы** (`rediss://`) — managed Redis (Upstash) требует и то, и другое; без этого подключение к нему не проходило бы аутентификацию.
- **`lockDuration: 20 минут`** на воркере анализа (`analysis.processor.ts`) — синхронный ONNX-инференс блокирует event loop на минуты, из-за чего дефолтный `lockDuration` BullMQ (30с) не успевал продлеваться и задача считалась "зависшей", перезапускаясь повторно, хотя первый запуск ещё не закончился.
- **Каналы обрабатываются последовательно, а не через `Promise.all`** — на Render free tier (512MB RAM) параллельная загрузка Whisper и SER-модели сразу для двух каналов приводила к нехватке памяти и перезапуску контейнера прямо посреди анализа.
- **`StorageService`/`GroqClient` не падают в конструкторе, если переменные окружения не заданы** — ошибка возникает только при реальной попытке использовать сервис (defensive init pattern), чтобы отсутствие одной внешней зависимости не роняло весь остальной API.

## 8. Известные ограничения (осознанные, не баги)

- **SER-модель тональности англоязычная** — см. раздел 5.3. Точность на русской речи не валидировалась количественно.
- **Groq — единственный не-self-hosted компонент.** Все остальные ML-модели работают локально в контейнере бесплатно; для GPT-функций взят внешний API, потому что self-hosted LLM (Ollama) физически не помещается в 512MB RAM бесплатного тарифа Render, а переезд на другой хостинг ради этого — отдельная задача, которая пока не стоит того. У Groq есть бесплатный лимит запросов.
- **`whisper-tiny`, не `whisper-small`/`base`** — компромисс между качеством распознавания и потреблением памяти/времени на бесплатном тарифе.
- **`GET api/v2/dashboard`**: `offset`/`limit` применяются только к `operatorRatingData` (списку операторов), остальные агрегаты (`summaryData`, `plotData`, `negativeHistogramData`) считаются по всей выборке за период — так осмысленнее для агрегатов, но стоит иметь в виду при чтении контракта.

## 9. Как это всё поднять локально

Подробности — в [README.md](./README.md). Коротко: `docker compose up -d --build` поднимает Postgres, Redis, MinIO и сам API одной командой, миграции и сид применяются автоматически при старте контейнера.

## 10. Переменные окружения

Полный список с комментариями — в `.env` (не в git) и `docker-compose.yml` (дефолты для локального запуска). Основные группы:

| Группа | Переменные | Обязательна на проде |
|---|---|---|
| БД | `DATABASE_URL` | да |
| JWT | `JWT_SECRET`, `JWT_EXPIRES_IN` | да |
| Redis (очередь) | `REDIS_URL` | нет — без неё загрузка звонков работает, просто анализ не запускается |
| S3-хранилище | `S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_BUCKET` | нет — без неё всё работает, кроме загрузки звонков |
| Groq | `GROQ_API_KEY` | нет — без неё всё работает, кроме `POST .../gpt-analysis` |

Такая "мягкая" деградация (а не падение всего процесса при старте) — намеренный паттерн, см. раздел 7.
